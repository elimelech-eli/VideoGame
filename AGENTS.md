# Delivery workflow

- Agree on a short acceptance checklist. Implement the requested scope; flag material scope growth before adding it.
- During iteration, run affected checks (`scripts/Test-Local.ps1 -Suite Core|EditMode|PlayMode`, optionally `-TestFilter`). Default `-Suite All` remains the final full Unity check.
- For gameplay changes, finish with one complete local suite and the relevant player build/smoke/visual checks. Repeat wider validation only when a later change invalidates its evidence. CI/docs-only changes need tooling checks, not local Unity builds.
- Review the final diff, input edge cases and `git diff --check` before pushing. Check native command exit codes explicitly in PowerShell.
- Branch pushes run fast checks. Open the PR without waiting for a branch Unity build; full Unity tests, Windows build and player smoke run on the PR and master. Documentation-only PR/master changes skip expensive jobs with an explicit scope summary.
- Preserve the three required branch-protection checks. Merge only after the current PR checks pass; verify master afterward.
- Use `scripts/Watch-CI.ps1 -RunId <id>` for bounded monitoring. Report transitions/failures/completion; do not repeatedly inspect unchanged jobs or re-review completed work while waiting.
- Keep tool output narrow. For each delivery, report local validation time, remote job durations, and full test/build counts when available. Account usage has no reliable per-PR attribution; do not invent it.
- A delivery is not complete until D:\VideoGame\Builds\Windows contains the complete playable artifact for the latest verified remote master. Refresh the whole player folder from successful master CI (or an exact-master build), preserve the previous working build until replacement passes smoke, and record the source commit/run in BUILD-INFO.json. Feature/review builds belong outside this standard folder. Documentation-only master commits may reuse an unchanged player artifact only with an explicit source/content-equivalence record.
- See docs/DEVELOPMENT.md for the pipeline and manual smoke checklist.

# Environment assembly and visual review

- For a fixed spaceship, establish the hull silhouette, fore/aft orientation, axial circulation and command-deck proportions before furnishing. Compartments follow the vessel's envelope; avoid attaching independent rectangular rooms and calling the result a ship.
- Plan the Nexus's eventual expanded layout before finalizing its starting layout. Reserve actual space and circulation for future rooms/areas, show meaningful sealed access, and distinguish starting accessible space from future space in visual reviews. Do not furnish the entire current envelope as permanently occupied starter space or count cosmetic upgrades as room expansion. Specific expansion layout and unlock costs remain design decisions requiring review.
- The cutter envelope currently represents the ship's forward section: bridge with mission selection/piloting at the bow, port scanners/targeting operations, basic captain's quarters to starboard, and aft cargo. Keep the spine and cargo center route clear to a rear expansion hatch. Later engineering, crafting and companion accommodation belong to future sections unless the user changes this allocation.
- The Nexus ship is a fixed authored layout. Fit each junction deliberately; modular assets are construction pieces, not a reason to accept gaps or awkward joins.
- A shared asset pack does not guarantee visual compatibility. Keep each compartment's floors, walls, trim and wear coherent. Change material families together at an architectural boundary such as a bulkhead doorway; align the floor transition with its threshold.
- Measure imported Unity bounds, pivots, facing and contact planes before assembly. Do not infer placement from another format's axes or compensate with arbitrary per-piece scaling. Fit wall sections to the actual door frame and use compatible junction pieces.
- Isometric cutaways need solid-looking thickness, finished top/end caps and clean corners. Never leave single-sided sheets, exposed backs, gaps, intersecting supports or floating details in a presented review.
- Before presenting, inspect actual Unity renders at the gameplay angle/zoom and a closer view. Check every wall/frame/corner connection, floor seam, material transition, player scale and visibility. Fix visible assembly defects before asking the user to review.
- Check seating faces its workstation. Add lived-in detail through purposeful equipment/storage/personal items around room edges while preserving door approaches, the spine and future expansion access; distinguish deliberate starter sparseness from unfinished assembly.

See `docs/NEXUS_SHIP_REVIEW.md` for scope and evidence. Approval covers this foundation; the full ship layout still requires its planned review before gameplay integration.

Preserve its fixed layout and rear expansion boundary. Imported door trim needs fitted side/header collision with a clear floor; shallow grilles/cables must not snag the character. Validate actual CharacterController doorway crossing as well as static route clearance.
